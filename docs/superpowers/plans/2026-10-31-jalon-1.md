# Jalon 1 « La première soirée » — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Up to 10 friends connect a Bevy client to a central server, create a D&D-SRD hero, and dig their own mountain fortress (top-down, Z-levels) while dwarves controlled by a separate AI service dig designated zones. The world persists and keeps running while players are offline.

**Architecture:** This is a Cargo workspace. `moria-core` is the shared library: types, pathfinding, wire protocol and AI messages. `moria-server` is the single authoritative central server. It runs a fixed 10 Hz tick over every mountain, owns the physical world state, persists it to one file, and accepts clients over TCP. `moria-dwarf-ai` is the first concept service: it receives a mountain view over NATS once per second and answers with dwarf→task assignments, which the server validates and executes. `moria-worldgen` is a one-shot container that generates the world file. `moria-client` is the Bevy client.

**Tech Stack:** Rust 1.98 (edition 2024), Bevy 0.20, bevy_egui 0.43 (use the version pair that bevy_egui's README lists as compatible), tokio, async-nats 0.51, NATS 2.x Docker image, serde + postcard (wire and save format), argon2 (passwords), rand + rand_chacha (seeded generation), Docker Compose (deployed as a Portainer stack).

**Spec:** `docs/superpowers/specs/2026-10-31-moria-design.md`

## Global Constraints

- Rust everywhere. Every crate lives in the root workspace and uses `edition = "2024"`.
- Players: at most **10 simultaneous** connections. The 11th gets `Reject::ServerFull`.
- No PvP. A client can only act on its own mountain. The server ignores any client message that targets another mountain.
- Tick: **10 Hz** (100 ms). Nothing in the tick may await the network, NATS or the disk. Saves happen on a snapshot clone, off the tick task.
- The simulation runs **for all mountains at all times**, whether or not their owner is connected.
- If the dwarf-ai service is absent, the game keeps running: dwarves finish their current task and then idle. When the service comes back, they resume.
- Only one port is exposed to the internet: the server's TCP port **7777**. NATS and the other services stay on the internal Docker network.
- Rendering is **colored squares** only. Colors come from one `tile_color()` function so they can later be swapped for images.
- Every user-facing text is in **French**.
- `PROTOCOL_VERSION: u32 = 1` lives in `moria-core`. Client and server refuse each other on mismatch.
- The SRD 5.1 attribution (CC-BY-4.0) must be present in `ATTRIBUTION.md` and on the client's hero-creation screen.

## Review Focus

1. **A dwarf assigned to a tile that the player or hero digs first.** The server must drop the task and free the dwarf. It must not leave the dwarf "busy" forever. → test in Task 5 `task_dropped_when_target_already_dug`.
2. **A designation over tiles that are already open, or over a tile a dwarf or the hero stands on.** Open tiles are ignored. An occupied tile is never dug as stairs. → tests in Task 3 `designate_skips_open_tiles` and Task 5 `stairs_never_dug_under_occupant`.
3. **A player reconnecting while their dwarves have kept working.** The client must receive a full fresh snapshot, never deltas against stale state. → test in Task 7 `reconnect_receives_snapshot_with_offline_progress`.
4. **A truncated, oversized or garbage frame from a client.** The server drops that connection and nobody else's. → test in Task 6 `oversized_frame_disconnects_only_that_client`.
5. **A crash in the middle of a save.** The previous save must still load. → test in Task 4 `save_is_atomic`.

- `struct Resources { stone: u32, gold: u32, mithril: u32 }` with `fn add(&mut self, other: Resources)`
- `enum DesignationKind { Dig, Stairs }`
- `struct Mountain { pub id: MountainId, w: i16, h: i16, d: u8, tiles: Vec<Tile>, pub designations: BTreeMap<TilePos, DesignationKind> }`
  - `fn new(id, w, h, d, fill: Tile) -> Self`, `fn get(&self, p) -> Option<Tile>`, `fn set(&mut self, p, t)`, `fn in_bounds(&self, p) -> bool`
  - `fn walkable(&self, p) -> bool`: Floor or Stair
  - `fn can_move(&self, from, dir) -> bool`: horizontal moves go to a walkable tile. `Up`/`Down` need Stair at both ends.
  - `fn designate(&mut self, a: TilePos, b: TilePos, kind) -> usize`: covers the rectangle at `a.z`. It only adds **solid** tiles, and for `Stairs` also needs `z < d-1`. Returns the count added.

- `MOUNTAIN_W = 48, MOUNTAIN_H = 48, MOUNTAIN_D = 8`

Note: `z` grows downward (0 = surface). `Dir::Down` = `z + 1`.

### Task 4: Dwarf AI assignment (pure logic + NATS service)

**Files:**
- Create: `crates/moria-dwarf-ai/{Cargo.toml,src/main.rs,src/assign.rs}`

**Interfaces — Consumes:** `AiView`, `Assignments`, `find_path`, `work_spot_goal`. **Produces:**
- `assign::assign(view: &AiView) -> Vec<(DwarfId, TilePos)>`
- Binary: connects to `NATS_URL` (default `nats://nats:4222`), subscribes to `SUBJECT_VIEW` in NATS **queue group `"dwarf-ai"`** (so each view is handled once when the service is scaled), and publishes `assign()` results on `SUBJECT_ASSIGN`. It retries the connection forever with 2 s backoff, and logs with `tracing`.

**Algorithm (the "nains intelligents" contract):** the open tasks are the designations, minus `claimed`, minus targets where any `occupied` tile *is* the target. Repeat until no idle dwarf can reach any open task: for each idle dwarf, run one BFS to find its nearest open task (path length to a work spot). Pick the globally shortest (dwarf, task) pair, assign it, and remove both. Ties break by lowest DwarfId, then lowest TilePos. A task with no reachable work spot is not assigned and stays open.

### Task 5: Server simulation tick

**Files:**
- Create: `crates/moria-server/{Cargo.toml,src/sim.rs}`

**Interfaces — Consumes:** `World`, `Mountain`, `find_path`, `hero_dig_ticks`, `Assignments`. **Produces:**
- `enum Command { Move(Dir), Dig(Dir), Designate { a, b, kind }, Cancel { a, b } }`. This is `ClientMsg` minus the handshake messages.
- `sim::apply_command(w: &mut World, m: MountainId, c: Command)`. Hero movement uses `can_move` and the move cooldown (2 ticks). Moving and digging are mutually exclusive: a Move cancels the current DigJob. `Dig(dir)` starts a DigJob on `hero.pos.step(dir)` if that tile is solid. Down-dig of stairs is not available to the hero in J1 (only Designate Stairs).
- `sim::apply_assignments(w: &mut World, a: &Assignments)`. It ignores a pair when the dwarf isn't idle, the target isn't designated, the target is already claimed, or there is no path to a work spot. Otherwise it stores a `DwarfTask` with that path.
- `sim::step(w: &mut World) -> BTreeMap<MountainId, TickDelta>`: advances every mountain by one tick. Hero DigJob progress uses `hero_dig_ticks`. Dwarves move 1 tile every 2 ticks along their path, then dig on arrival (dig ticks from the Shared numbers table). On completion it calls `Mountain::dig`, adds the resources to the fortress, and clears the task. The delta includes tile changes and designation changes.
- Task invalidation: at the start of each dwarf update, if the target is no longer designated or no longer solid, the task is dropped. If the next path tile is no longer walkable, the dwarf re-paths once and drops the task if that fails.
- `sim::claimed(w, m) -> Vec<TilePos>` and `sim::occupied(w, m) -> Vec<TilePos>` (the hero and all dwarves), used to build `AiView`.

### Task 6: Server networking, auth, NATS bridge, main loop

**Files:**
- Create: `crates/moria-server/src/{main.rs,net.rs,bridge.rs}`

**Interfaces — Consumes:** Tasks 2–5. **Produces:**
- Env/flags: `MORIA_DATA` (default `/data/world.bin`), `MORIA_BIND` (default `0.0.0.0:7777`), `NATS_URL` (default `nats://nats:4222`). The server **exits with an error** when the world file is missing. The message says: "lancez d'abord moria-worldgen".
- Architecture: one tokio task owns `World` and runs the 100 ms `tokio::time::interval` loop (`MissedTickBehavior::Skip`). Every tick it drains, without blocking, an `mpsc` of `(PlayerId, Command)` and an `mpsc` of `Assignments`, runs `sim::step`, and sends each delta to the connected client of that mountain through a per-session `mpsc::Sender<ServerMsg>` (`try_send`: a full channel disconnects that slow client). Every 10 ticks it builds one `AiView` per mountain *in rotation* (one mountain per tick), and hands it to the bridge through a bounded channel with `try_send`. A dropped view is fine.
- `bridge.rs`: connects to NATS with retry in its own task. It publishes the views and forwards the decoded `Assignments` into the mpsc. While NATS is down, it drops the views.
- Saver: every 300 ticks and on Ctrl-C/SIGTERM, the world task clones `World` and calls `spawn_blocking(save)`. On a shutdown signal it awaits the final save and then exits.
- `net.rs` session: read the first frame. It must be `Hello`, within 10 s. Then apply these checks in order: version mismatch → `Reject::VersionMismatch{server: PROTOCOL_VERSION}`; name not 3–16 chars of `[A-Za-z0-9_-]` → `InvalidName`; already 10 sessions → `ServerFull`; unknown name → create the account (argon2 hash) and claim a mountain (`NoFreeMountain` if none left); known name with a wrong password → `BadPassword`. Then send `Welcome`. If the hero is None, the client must send `CreateHero` next: store the hero with `roll_abilities` at the first entrance tile. ### Task 8: Bevy client

**Files:**
- Create: `crates/moria-client/{Cargo.toml,src/main.rs,src/net.rs,src/ui.rs,src/render.rs,src/input.rs}`

**Interfaces — Consumes:** `moria-core` protocol, `Mountain`, `srd`. **Produces:**
- `net.rs`: `connect(addr: String) -> NetHandle { tx: Sender<ClientMsg>, rx: Receiver<ServerMsg> }` (std threads + `std::sync::mpsc`, blocking `read_frame`). A Bevy system drains `rx` every frame.
- States: `Login → CreateHero (only if needs_hero) → Playing`, plus a `Disconnected` screen that shows the reason in French.
- `ui.rs` (egui). The Login screen has the server address (default `127.0.0.1:7777`, remembered in a local file next to the binary), the name and the password. The CreateHero screen has race and class combos, a stats preview from `roll_abilities`, and the SRD attribution text. Rejects map to French messages: "Version différente du serveur (serveur v{n}) — mettez le client à jour", "Mot de passe incorrect", "Serveur plein (10 joueurs)", "Plus de montagne libre", "Nom invalide (3–16 caractères : lettres, chiffres, _ ou -)".
- `render.rs`: `pub fn tile_color(t: Tile) -> Color` with the palette of the approved mockup: Rock `#6b6b6b`, Floor `#3a2a1e`, Gold `#c9a227`, Mithril `#4fa3d1`, Stair `#8b5a2b`. Tiles are 16 px. Only `current_z` is drawn. The hero is a red `@`, and dwarves are a white `n` on the floor color. Designations are a yellow outline (Dig) or a cyan one (Stairs). The camera follows the hero, and `current_z` follows the hero's z unless the player is browsing levels. The HUD shows the level (`Niveau Z {z}`), the resources (`Pierre / Or / Mithril`), the hero's name, race and class, and the active designation mode.
- `input.rs`: WASD/arrows → `Move`. `<`/`>` → `Move(Up/Down)` when standing on stairs; otherwise they browse levels. Space + direction → `Dig` toward the last move direction. `D`/`X` select the designation mode (Dig/Stairs). Left-drag designates a rectangle on `current_z`, and right-drag cancels. **Prediction:** a `Move` the local `can_move` accepts is applied immediately to the shown hero position. Each `Tick` sets the authoritative position (this is the reconciliation, which is enough for one-tile steps).
